# Die asset register + Die Shots Report — what they are and what we can build from them

**Date:** 2026-09-12
**Sources:**
- `reference/Copy of Asset #'s for Dies.xlsx` (received 2026-09-12)
- `reference/Aug 17_ 2026 Die Shots Report.html` (saved 2026-09-12, report as-of 8/18/2026)

**Outputs:** `reference/seed_data/die_roster.csv`, `reference/seed_data/die_cavities.csv`,

## 1. The asset register

MPP's fixed-asset register for tooling. Two sheets, four columns
(`Tag # | Description | VENDOR | DATE`).

| Sheet | Tags allocated | Populated |
|---|---|---|
| Die Mold | DM0001–DM0210 | 170 |
| Trim Die | TD0001–TD0063 | 28 |

The trailing empty rows are **pre-allocated tag numbers**, not missing data.
`DATE` is the acquisition / PO date — the series starts 2019-01-28 and runs to
2026-08-20 at a steady 20–28 dies a year.

`Description` is an implicit three-part key:

```
<part family>  <component>  die <generation letter>
     59B          C/H #2,3,4      die "K"
```

The **generation letter** is the important field. Dies are replaced
alphabetically, so `59B/5PA Fuel Pump` walks L → M → N → … → W across
DM0001…DM0092. It is the only thing that distinguishes one physical die from
its predecessor.

### Register data quality

- **Vendor names are free text** — 20 spellings for 8 real vendors
  (`Accu-Die` / `Accudie` / `Accu Die` / `Accu- die` / `Accudie-Die`;
  `MEIWA MOLD` / `Meiwa` / `Meiwa Mold International`). Normalised in the parser.
- **Two trim dies are filed on the Die Mold sheet** — `DM0087 6MDW manifold trim #1`
  and `DM0088 4 cavity 5GO trim # 1`.
- **Descriptions degrade over time.** Early rows are complete
  (`59B C/H IN/EX 1,5 die G`); later rows drop the component, the family, or
  both — `DM0108` is literally `2,3,4 M`, `DM0132` is `64A G`. 44 rows needed a
  hand-written restatement (`DESC_FIX` in the parser, each read off its
  neighbours in the same generation). **These are the rows MPP should restate
  before we treat the register as a system of record.**

## 2. The Die Shots Report

A saved page from the legacy MES. The source URL is in the file:

```
http://backupsrv.mppnet.com/mpp/DieCast/DieShotsReport.aspx?date=8/18/2026&status=0
```

It is **parameterised by date and status**, so the legacy DB holds this data
queryable as-of — we should pull the underlying table off EXCSRV05
(`MES` / `EMMD`, see `project_mpp_legacy_source_system`) rather than scrape the
page. The PDF copy is the same report 12 days earlier, which gives a delta if a
shots/day rate is ever wanted.

343 data rows under 9 customer group headers: Honda Anna (183), Honda (140),
plus Aisin / American Honda / Astemo / Elesys / EMP / FPI / Honda Alabama.

### Status legend (from the page footer)

| Code | Meaning | Rows |
|---|---|---|
| `C` | Current | 103 |
| `B` | Backup | 73 |
| `W` | Waiting for Approval | 166 |
| `A` | Approved | 1 |
| `O` | OutSourced | 0 |

### The red "Shot Life Planned" cell

Reverse-engineered exactly — 0 mismatches across all 343 rows:

```
red  <=>  Status <> 'B'  AND  GoodShots > ShotLifePlanned
```

Two things worth noting: it tests **Good** shots, not Total; and it silently
exempts Backup dies, so a backup die sitting well over its planned life is never
flagged. 154 rows have `ShotLifePlanned = 0` (never configured) and therefore
trip the rule trivially.

## 3. The structural catch — rows are part x die, not die

A die appears **once per part number it casts**. Everything downstream follows
from this:

- **`Total Dies in Mass Production: 103`** is a row count, not a die count.
  Collapsing duplicates gives **~62 physical dies** currently in mass production.
- **`Total Dies over Planned Life: 227`** is likewise 227 *rows*, and 153 of them
  are "over" only because their planned life is zero.

Worse, the shot number in those duplicate rows means **two different things**,
and nothing in the report says which:

**(a) Family die — one shot produces several part numbers at once.** The
counters are the same value. 59B cam holder die `K`:

| Parts | Total shots | Physical die |
|---|---|---|
| 187 (In No 1), 191 (In No 5), 192 (Ex 1), 196 (Ex 5) | 389,349 | `DM0059 59B C/H #1,5 die "K"` |
| 188/189/190 (In No 2,3,4), 193/194/195 (Ex 2,3,4) | 369,908 | `DM0060 59B C/H #2,3,4 die "K"` |

Two clusters on one letter = **two physical dies sharing generation K**. Die life
is the cluster value; summing would count it 6x.

**(b) Combo die — one die run for different part numbers on different
campaigns.** The counters *partition*. Fuel pump die `N`
(`DM0024 59B/5PA Fuel Pump die "N"`): 25,493 shots as `152-090 59B Base Comp
Fuel Pump` + 179,658 as `143-090 5PA Fuel Pump`. Here die life **is** the sum —
205,151 against a 200,000 planned life, which the report never flags because
neither row alone exceeds it.

### The counters drift

Within a family-die cluster the counts are near-identical but not equal — part
189 shows 216,434 where its siblings show 216,057; part 191 die M is 900 off.
The legacy system increments **per (part, die) row independently** rather than
holding one counter per die. That drift is unrecoverable noise in anything we
migrate; take the max of the cluster and move on.

### "Approved" is not a usable filter

Exactly **one** row in the whole report carries status `A`: part `656-090 6MAA
HOLDCOMP NO5 INTAKE`, die B. The other nine parts cast by that same physical die
are all `W`. It is a data-entry slip on one row of a ten-part cluster, not a
meaningful state. **Nothing at MPP is meaningfully "Approved" in this report.**

If the question is "which dies are approved for production", the answer is
`Current` + `Backup` — the dies past approval and in the pool — which is
**103 physical dies** (62 Current + 41 Backup).

## 4. Joining the two

There is **no shared identifier**. The only key is the human-readable
description, so the parser matches on:

1. part family, with aliases (`5BAA`=`5BA`, `64AA`=`64A`, `6FBA`=`6FB`,
   `6MAA`=`6MA`, `5G0`=`5GO`, `5J6-1`=`5J6`, `66VT`=`66V`, `6MDW`=`6MD`,
   `RNOX`=`RNO`)
2. component (OilPan / FuelPump / CamHolder / RockerShaft / …)
3. generation letter
4. then, where one key has several clusters (a die *set*), the **journal
   positions** (`#1,5` vs `#2,3,4`) and the **cam bank** (IN / EX / EX-Lower),
   or Single-vs-Dual for the Astemo tools

Result — 253 roster rows:

| | Count | |
|---|---|---|
| asset + report | 138 | tagged die, matched to its shot record |
| asset only | 60 | 30 trim dies (the report is die-cast only) + 30 die molds with no match |
| report only | 55 | **running dies with no MPP asset number** |

### The gap that matters

Whole part families appear in the report with **no asset tag at all**: 5A2, 5K8,
5LA, 5MH, RXO, RNA, RDJ, RNO, R1A, R5A, R70, SZAX, PGE, P8A. Most are Honda Anna
and other-customer parts, and several are *Current* dies with 200k+ shots on
them.

Two candidate explanations, and it matters which:

1. Those dies are **customer-owned / consigned**, so MPP never capitalised them —
   no asset number by design.
2. They **predate the register's 2019 start**.

(1) fits better — `5A2 Fuel Pump die T` is a recent Current die and still
untagged — but neither file settles it. **Question for MPP.**

## 5. Cavities — yes, we can model this

Each family-die cluster tells us exactly which part numbers that die casts, and
those are its cavities. Derived cavity counts across the roster:

| Cavities | Dies |
|---|---|
| 1 | 131 |
| 2 | 12 |
| 3 | 14 |
| 4 | 23 |
| 6 | 11 |
| 8 | 2 (both the RPY die-H ambiguity below) |

The schema already supports this — `Tools.ToolCavity` has `ItemId` (migration
`0072`) and `CavityCode NVARCHAR(4)` (migration `0076`). `die_cavities.csv` is
371 rows shaped for it: one row per (die, cavity) with the Macola part number.

**Caveat: the derived count is a LOWER BOUND.** It counts *distinct part numbers
cast per shot*. A die with four identical cavities making one part number —
`DM0088 4 cavity 5GO trim #1`, `DM0170 5GO N die 4 cavity` — collapses to 1,
because the report cannot see it. MPP has to supply the true cavity count for
single-part dies.

### Known unresolved

- `DM0157 RPY CamHolder 5,5,6 H` / `DM0158 RPY Cam Holder Intake H` — flagged
  AMBIGUOUS. The H generation has an Ex cluster and an Ex-Lower cluster but no
  Intake cluster in the report, so `DM0158` has no counterpart to match.

## 6. What this means for the build

- **`Tools.Tool.ShotCount` / `ShotLimit` map straight onto the report**
  (`Good Shots` / `Shot Life Planned`). Our model is already the better one — a
  counter per *die* instead of per (part, die).
- **Legacy `C`/`B`/`W`/`A` does not map to `Tools.ToolStatusCode`**
  (`Active` / `UnderRepair` / `Scrapped` / `Retired`). It is a *mount-eligibility*
  axis — which generation is in service vs. on the shelf vs. not yet approved —
  orthogonal to condition. Needs an OI: either extend the code table or model it
  as a `ToolAttribute`.
- **There is no Seeding Registry item for the die master.** S-07 and S-08 cover
  die ranks and the compatibility matrix; nothing covers `Tools.Tool` itself.
  Added as **S-14**.
- Dev currently holds 17 `Tools.Tool` rows, mostly test fixtures. The die master
  is effectively unseeded.

## 7. Open questions for MPP

1. Are the untagged families (5A2, 5LA, 5MH, RNA, RDJ, RNO, R1A, R5A, R70, SZAX,
   PGE, P8A, 5K8, RXO) **customer-owned**, or just pre-2019?
2. **True cavity count for single-part dies** — the report only sees distinct
   part numbers, so any die with identical cavities reads as 1.
3. `Shot Life Planned = 0` on 154 rows — never configured, or deliberately
   unlimited?
4. Restate the ~44 degraded register descriptions (list in the parser's
   `DESC_FIX`).
5. Confirm `Current` + `Backup` is the right reading of "approved for
   production", given status `A` is a single stray row.
